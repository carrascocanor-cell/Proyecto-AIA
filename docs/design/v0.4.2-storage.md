# V0.4.2 — Historical Market Data Storage

**Estado:** diseño pendiente de revisión; no es una implementación.

**Base de diseño:** commit V0.4.1 `bcf525d56a47aa9b4b5ded496f19865d227cb897`.

## Alcance

V0.4.2 añadirá almacenamiento histórico de mercado en SQLite, sin migrar el CSV legado y sin mezclarlo con la futura contabilidad de paper trading. Se conservarán las versiones históricas, los proveedores y la procedencia de las importaciones. Solo se persistirán velas cerradas.

Quedan fuera de esta fase la contabilidad, paper trading, decisiones autónomas, noticias, dashboard, notificaciones y ejecución real. La ejecución real seguirá desactivada hasta una autorización futura específica.

## 1. Identidad: activo, instrumento, fuente y serie

Se distinguen cuatro conceptos:

- **Activo (`asset_id`)**: identidad canónica del activo subyacente; no es el ticker. En tokens, debe identificar la cadena y la dirección completa del contrato, por ejemplo `solana:<mint>`.
- **Instrumento (`instrument_id`)**: identidad estable de una representación negociable concreta, determinada por el activo, el mercado/listado y la moneda de cotización. BTC/USD y BTC/EUR son instrumentos distintos. Una acción listada en dos mercados puede tener dos instrumentos vinculados al mismo activo.
- **Fuente (`source_id`)**: una asociación concreta entre instrumento, proveedor, símbolo del proveedor y feed/origen. Los símbolos son etiquetas de origen, nunca claves de identidad canónica.
- **Serie (`series_id`)**: una fuente y un instrumento con intervalo, base de ajuste y unidad de volumen determinados. Las series de proveedores distintos no se combinan.

`asset_id`, `instrument_id`, `market`, `provider`, `provider_symbol` y direcciones se comparan como texto `BINARY`: no se convierten a minúsculas ni se normalizan. La moneda de cotización conserva la convención existente de código en mayúsculas.

### Compatibilidad con `Instrument` V0.4.1

El `Instrument` actual incluye `provider` y `provider_symbol`, aunque son propiedades de la fuente y no de la identidad canónica. En la base:

- `instrument_id`, activo, clase de activo, mercado, moneda de cotización, calendario, zona y convención temporal viven en `instruments`/`assets`.
- `provider`, `provider_symbol` y `source` viven en `data_sources`.
- Para reconstruir el modelo existente se combina la identidad canónica con la fuente seleccionada.

Se propone añadir a `Instrument` un campo opcional `asset_id` al final de la clase. Los usos actuales seguirían siendo válidos. Si falta, la capa de almacenamiento usa `instrument_id` como `asset_id`; no deduce identidades a partir de símbolos. Dos instancias del mismo instrumento para proveedores distintos deben coincidir en todos los campos canónicos, aunque difieran proveedor y símbolo.

Las filas de `assets`, `instruments`, `data_sources` y `series` son identidades append-only: se pueden insertar identidades nuevas, pero no actualizar ni borrar las existentes. Si cambia un atributo que modifica la identidad o la interpretación de datos, se registra una identidad nueva. Una corrección excepcional de metadatos históricos requiere una migración explícita, con backup, auditoría y revisión; no una actualización silenciosa.

## 2. Esquema SQLite

SQLite forma parte de la biblioteca estándar y es adecuado para un almacenamiento local con escrituras serializadas. Tiene un único escritor efectivo a la vez; para muchas escrituras concurrentes se reevaluaría el motor. Los precios y volúmenes se almacenan en `TEXT`, nunca en `REAL`.

El esquema contiene exactamente estas seis tablas: `assets`, `instruments`, `data_sources`, `series`, `ingestion_batches` y `bar_versions`. No incluye `legacy_close_versions`: el CSV legado no se importará. Los IDs y referencias textuales obligatorias rechazan valores vacíos o con espacios exteriores, pero no se normalizan. `COLLATE BINARY` conserva distinciones de mayúsculas, incluidas las direcciones Solana.

El SQL de abajo define tablas, claves, restricciones, índices y triggers. Las validaciones exactas de Decimal, OHLC, fechas y secuencias se hacen también en Python antes de insertar; SQLite no puede comparar decimales arbitrarios exactamente sin convertirlos a `REAL`.

```sql
CREATE TABLE assets (
    asset_id TEXT COLLATE BINARY PRIMARY KEY
        CHECK (length(asset_id) > 0 AND asset_id = trim(asset_id)),
    asset_class TEXT NOT NULL CHECK (
        asset_class IN ('cryptocurrency', 'equity', 'etf', 'index', 'solana_token')
    )
);

CREATE TABLE instruments (
    instrument_id TEXT COLLATE BINARY PRIMARY KEY
        CHECK (length(instrument_id) > 0 AND instrument_id = trim(instrument_id)),
    asset_id TEXT COLLATE BINARY NOT NULL
        REFERENCES assets(asset_id) ON UPDATE RESTRICT ON DELETE RESTRICT,
    market TEXT COLLATE BINARY NOT NULL
        CHECK (length(market) > 0 AND market = trim(market)),
    quote_currency TEXT COLLATE BINARY NOT NULL
        CHECK (
            length(quote_currency) BETWEEN 2 AND 16
            AND quote_currency = upper(quote_currency)
            AND quote_currency = trim(quote_currency)
        ),
    trading_calendar TEXT COLLATE BINARY NOT NULL
        CHECK (length(trading_calendar) > 0 AND trading_calendar = trim(trading_calendar)),
    timezone TEXT COLLATE BINARY NOT NULL
        CHECK (length(timezone) > 0 AND timezone = trim(timezone)),
    session_close_convention TEXT NOT NULL CHECK (
        session_close_convention IN (
            'utc_interval_boundary', 'local_exchange_close'
        )
    ),
    UNIQUE (asset_id, market, quote_currency)
);

CREATE TABLE data_sources (
    source_id TEXT COLLATE BINARY PRIMARY KEY
        CHECK (length(source_id) > 0 AND source_id = trim(source_id)),
    instrument_id TEXT COLLATE BINARY NOT NULL
        REFERENCES instruments(instrument_id) ON UPDATE RESTRICT ON DELETE RESTRICT,
    provider TEXT COLLATE BINARY NOT NULL
        CHECK (length(provider) > 0 AND provider = trim(provider)),
    provider_symbol TEXT COLLATE BINARY NOT NULL
        CHECK (length(provider_symbol) > 0 AND provider_symbol = trim(provider_symbol)),
    source_name TEXT COLLATE BINARY NOT NULL
        CHECK (length(source_name) > 0 AND source_name = trim(source_name)),
    UNIQUE (instrument_id, provider, provider_symbol, source_name)
);

CREATE TABLE series (
    series_id TEXT COLLATE BINARY PRIMARY KEY
        CHECK (length(series_id) > 0 AND series_id = trim(series_id)),
    source_id TEXT COLLATE BINARY NOT NULL
        REFERENCES data_sources(source_id) ON UPDATE RESTRICT ON DELETE RESTRICT,
    interval TEXT NOT NULL CHECK (interval IN ('1m', '1h', '1d')),
    adjustment_type TEXT NOT NULL CHECK (
        adjustment_type IN (
            'raw', 'split_adjusted', 'split_and_dividend_adjusted',
            'total_return_adjusted'
        )
    ),
    volume_unit TEXT COLLATE BINARY
        CHECK (volume_unit IS NULL OR
               (length(volume_unit) > 0 AND volume_unit = trim(volume_unit)))
);

CREATE UNIQUE INDEX uq_series_definition
    ON series(source_id, interval, adjustment_type, COALESCE(volume_unit, ''));

CREATE TABLE ingestion_batches (
    batch_id TEXT COLLATE BINARY PRIMARY KEY
        CHECK (length(batch_id) > 0 AND batch_id = trim(batch_id)),
    series_id TEXT COLLATE BINARY NOT NULL
        REFERENCES series(series_id) ON UPDATE RESTRICT ON DELETE RESTRICT,
    status TEXT NOT NULL CHECK (
        status IN ('started', 'succeeded', 'failed', 'abandoned')
    ),
    started_at_utc TEXT NOT NULL CHECK (
        length(started_at_utc) = 27
        AND started_at_utc GLOB
            '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]T[0-9][0-9]:[0-9][0-9]:[0-9][0-9].[0-9][0-9][0-9][0-9][0-9][0-9]Z'
    ),
    received_at_utc TEXT CHECK (
        received_at_utc IS NULL OR (
            length(received_at_utc) = 27
            AND received_at_utc GLOB
                '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]T[0-9][0-9]:[0-9][0-9]:[0-9][0-9].[0-9][0-9][0-9][0-9][0-9][0-9]Z'
        )
    ),
    completed_at_utc TEXT CHECK (
        completed_at_utc IS NULL OR (
            length(completed_at_utc) = 27
            AND completed_at_utc GLOB
                '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]T[0-9][0-9]:[0-9][0-9]:[0-9][0-9].[0-9][0-9][0-9][0-9][0-9][0-9]Z'
        )
    ),
    source_reference TEXT COLLATE BINARY
        CHECK (source_reference IS NULL OR
               (length(source_reference) > 0 AND source_reference = trim(source_reference))),
    raw_payload_sha256 TEXT CHECK (
        raw_payload_sha256 IS NULL OR
        (length(raw_payload_sha256) = 64
         AND raw_payload_sha256 NOT GLOB '*[^0-9a-f]*')
    ),
    rows_received INTEGER NOT NULL DEFAULT 0 CHECK (rows_received >= 0),
    rows_inserted INTEGER NOT NULL DEFAULT 0 CHECK (rows_inserted >= 0),
    rows_revised INTEGER NOT NULL DEFAULT 0 CHECK (rows_revised >= 0),
    rows_unchanged INTEGER NOT NULL DEFAULT 0 CHECK (rows_unchanged >= 0),
    error_type TEXT
        CHECK (error_type IS NULL OR
               (length(error_type) > 0 AND error_type = trim(error_type))),
    error_message TEXT,
    CHECK (rows_inserted + rows_revised + rows_unchanged <= rows_received),
    CHECK (
        status <> 'succeeded'
        OR rows_inserted + rows_revised + rows_unchanged = rows_received
    ),
    CHECK (
        status NOT IN ('failed', 'abandoned')
        OR (rows_inserted = 0 AND rows_revised = 0 AND rows_unchanged = 0)
    ),
    CHECK (
        (status = 'started'
         AND completed_at_utc IS NULL
         AND error_type IS NULL
         AND error_message IS NULL)
        OR
        (status = 'succeeded'
         AND completed_at_utc IS NOT NULL
         AND error_type IS NULL
         AND error_message IS NULL)
        OR
        (status IN ('failed', 'abandoned')
         AND completed_at_utc IS NOT NULL
         AND error_type IS NOT NULL)
    ),
    UNIQUE (batch_id, status)
);

CREATE TABLE bar_versions (
    bar_version_id INTEGER PRIMARY KEY AUTOINCREMENT,
    series_id TEXT COLLATE BINARY NOT NULL
        REFERENCES series(series_id) ON UPDATE RESTRICT ON DELETE RESTRICT,
    bar_start_utc TEXT NOT NULL CHECK (
        length(bar_start_utc) = 27
        AND bar_start_utc GLOB
            '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]T[0-9][0-9]:[0-9][0-9]:[0-9][0-9].[0-9][0-9][0-9][0-9][0-9][0-9]Z'
    ),
    bar_end_utc TEXT NOT NULL CHECK (
        length(bar_end_utc) = 27
        AND bar_end_utc GLOB
            '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]T[0-9][0-9]:[0-9][0-9]:[0-9][0-9].[0-9][0-9][0-9][0-9][0-9][0-9]Z'
    ),
    session_date TEXT CHECK (
        session_date IS NULL OR (
            length(session_date) = 10
            AND session_date GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'
        )
    ),
    open_price TEXT NOT NULL CHECK (length(open_price) > 0),
    high_price TEXT NOT NULL CHECK (length(high_price) > 0),
    low_price TEXT NOT NULL CHECK (length(low_price) > 0),
    close_price TEXT NOT NULL CHECK (length(close_price) > 0),
    volume TEXT CHECK (volume IS NULL OR length(volume) > 0),
    status TEXT NOT NULL CHECK (status = 'closed'),
    provider_published_at_utc TEXT CHECK (
        provider_published_at_utc IS NULL OR (
            length(provider_published_at_utc) = 27
            AND provider_published_at_utc GLOB
                '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]T[0-9][0-9]:[0-9][0-9]:[0-9][0-9].[0-9][0-9][0-9][0-9][0-9][0-9]Z'
        )
    ),
    ingested_at_utc TEXT NOT NULL CHECK (
        length(ingested_at_utc) = 27
        AND ingested_at_utc GLOB
            '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]T[0-9][0-9]:[0-9][0-9]:[0-9][0-9].[0-9][0-9][0-9][0-9][0-9][0-9]Z'
    ),
    hash_version INTEGER NOT NULL CHECK (hash_version > 0),
    payload_sha256 TEXT NOT NULL CHECK (
        length(payload_sha256) = 64
        AND payload_sha256 NOT GLOB '*[^0-9a-f]*'
    ),
    revision_no INTEGER NOT NULL CHECK (revision_no >= 1),
    supersedes_version_id INTEGER UNIQUE
        REFERENCES bar_versions(bar_version_id) ON UPDATE RESTRICT ON DELETE RESTRICT,
    ingestion_batch_id TEXT COLLATE BINARY NOT NULL
        CHECK (length(ingestion_batch_id) > 0 AND ingestion_batch_id = trim(ingestion_batch_id)),
    batch_commit_state TEXT NOT NULL DEFAULT 'succeeded'
        CHECK (batch_commit_state = 'succeeded'),
    CHECK (bar_start_utc < bar_end_utc),
    CHECK (
        (revision_no = 1 AND supersedes_version_id IS NULL)
        OR (revision_no > 1 AND supersedes_version_id IS NOT NULL)
    ),
    UNIQUE (series_id, bar_start_utc, revision_no),
    UNIQUE (ingestion_batch_id, series_id, bar_start_utc),
    FOREIGN KEY (ingestion_batch_id, batch_commit_state)
        REFERENCES ingestion_batches(batch_id, status)
        ON DELETE RESTRICT DEFERRABLE INITIALLY DEFERRED
);

CREATE INDEX ix_bars_series_start_ingested_order
    ON bar_versions(series_id, bar_start_utc, ingested_at_utc, bar_version_id DESC);

CREATE INDEX ix_bars_series_ingested
    ON bar_versions(series_id, ingested_at_utc, bar_start_utc);

CREATE INDEX ix_batches_series_started
    ON ingestion_batches(series_id, started_at_utc);

CREATE TRIGGER bar_versions_check_revision_chain
BEFORE INSERT ON bar_versions
WHEN
    (NEW.revision_no = 1 AND (
        NEW.supersedes_version_id IS NOT NULL
        OR EXISTS (
            SELECT 1 FROM bar_versions old
            WHERE old.series_id = NEW.series_id
              AND old.bar_start_utc = NEW.bar_start_utc
        )
    ))
    OR
    (NEW.revision_no > 1 AND NOT EXISTS (
        SELECT 1 FROM bar_versions previous
        WHERE previous.bar_version_id = NEW.supersedes_version_id
          AND previous.series_id = NEW.series_id
          AND previous.bar_start_utc = NEW.bar_start_utc
          AND previous.revision_no = NEW.revision_no - 1
    ))
BEGIN
    SELECT RAISE(ABORT, 'invalid bar revision chain');
END;

CREATE TRIGGER bar_versions_validate_ingest_time
BEFORE INSERT ON bar_versions
BEGIN
    SELECT CASE WHEN NOT EXISTS (
        SELECT 1 FROM ingestion_batches batch
        WHERE batch.batch_id = NEW.ingestion_batch_id
          AND batch.series_id = NEW.series_id
          AND batch.status = 'started'
          AND NEW.ingested_at_utc >= batch.started_at_utc
          AND (
              batch.received_at_utc IS NULL
              OR NEW.ingested_at_utc >= batch.received_at_utc
          )
    )
    THEN RAISE(ABORT, 'ingestion time precedes its batch or receipt') END;

    SELECT CASE WHEN EXISTS (
        SELECT 1 FROM bar_versions same_batch
        WHERE same_batch.ingestion_batch_id = NEW.ingestion_batch_id
          AND same_batch.ingested_at_utc <> NEW.ingested_at_utc
    )
    THEN RAISE(ABORT, 'all bars in a batch must share one ingestion time') END;

    SELECT CASE WHEN EXISTS (
        SELECT 1 FROM bar_versions previous
        WHERE previous.series_id = NEW.series_id
          AND previous.ingestion_batch_id <> NEW.ingestion_batch_id
          AND previous.ingested_at_utc >= NEW.ingested_at_utc
    )
    THEN RAISE(ABORT, 'ingestion time must advance beyond prior batches in the series') END;
END;

CREATE TRIGGER bar_versions_match_started_batch
BEFORE INSERT ON bar_versions
WHEN NOT EXISTS (
    SELECT 1 FROM ingestion_batches batch
    WHERE batch.batch_id = NEW.ingestion_batch_id
      AND batch.series_id = NEW.series_id
      AND batch.status = 'started'
)
BEGIN
    SELECT RAISE(ABORT, 'bar version requires its started ingestion batch');
END;

CREATE TRIGGER bar_versions_no_update
BEFORE UPDATE ON bar_versions
BEGIN
    SELECT RAISE(ABORT, 'bar versions are immutable');
END;

CREATE TRIGGER bar_versions_no_delete
BEFORE DELETE ON bar_versions
BEGIN
    SELECT RAISE(ABORT, 'bar versions are immutable');
END;

CREATE TRIGGER ingestion_batches_terminal_once
BEFORE UPDATE ON ingestion_batches
WHEN OLD.status <> 'started' OR NEW.status = 'started'
BEGIN
    SELECT RAISE(ABORT, 'ingestion batch is already terminal');
END;

CREATE TRIGGER ingestion_batches_validate_finalization
BEFORE UPDATE ON ingestion_batches
WHEN OLD.status = 'started'
 AND NEW.status IN ('succeeded', 'failed', 'abandoned')
BEGIN
    SELECT CASE WHEN
        NEW.batch_id IS NOT OLD.batch_id
        OR NEW.series_id IS NOT OLD.series_id
        OR NEW.started_at_utc IS NOT OLD.started_at_utc
    THEN RAISE(ABORT, 'batch identity and start time are immutable') END;

    SELECT CASE WHEN
        (OLD.source_reference IS NOT NULL
         AND NEW.source_reference IS NOT OLD.source_reference)
        OR (OLD.raw_payload_sha256 IS NOT NULL
            AND NEW.raw_payload_sha256 IS NOT OLD.raw_payload_sha256)
        OR (OLD.received_at_utc IS NOT NULL
            AND NEW.received_at_utc IS NOT OLD.received_at_utc)
    THEN RAISE(ABORT, 'batch provenance cannot be rewritten') END;

    SELECT CASE WHEN NEW.received_at_utc IS NOT NULL AND EXISTS (
        SELECT 1 FROM bar_versions bar
        WHERE bar.ingestion_batch_id = OLD.batch_id
          AND bar.ingested_at_utc < NEW.received_at_utc
    )
    THEN RAISE(ABORT, 'bar ingestion cannot precede batch receipt') END;

    SELECT CASE WHEN NEW.status IN ('failed', 'abandoned') AND EXISTS (
        SELECT 1 FROM bar_versions bar
        WHERE bar.ingestion_batch_id = OLD.batch_id
    )
    THEN RAISE(ABORT, 'failed or abandoned batches cannot retain bars') END;

    SELECT CASE WHEN NEW.status = 'succeeded'
        AND NEW.rows_inserted + NEW.rows_revised <> (
            SELECT COUNT(*) FROM bar_versions bar
            WHERE bar.ingestion_batch_id = OLD.batch_id
        )
    THEN RAISE(ABORT, 'successful batch counts must match inserted bar versions') END;
END;

CREATE TRIGGER ingestion_batches_no_delete
BEFORE DELETE ON ingestion_batches
BEGIN
    SELECT RAISE(ABORT, 'ingestion batches are append-only');
END;
```

### Justificación de las tablas

- `assets` identifica el activo sin depender de un ticker o proveedor.
- `instruments` identifica el mercado/listado y cotización concretos.
- `data_sources` conserva los símbolos y feeds específicos de cada proveedor.
- `series` impide mezclar fuente, intervalo, ajuste o unidad de volumen.
- `ingestion_batches` conserva procedencia, tiempos, resultado y errores de cada intento.
- `bar_versions` almacena observaciones inmutables y las revisiones históricas.

La unidad de volumen pertenece a la serie. `NULL` significa que la fuente no suministra volumen; el índice único con `COALESCE` evita crear definiciones duplicadas por la semántica especial de `NULL` en los índices únicos de SQLite.

Los triggers `*_must_be_immutable_*` impiden `UPDATE` y `DELETE` de las cuatro tablas de identidad; no impiden `INSERT` de instrumentos, fuentes o series nuevos. Un cambio de proveedor o símbolo se registra como una fuente nueva. Cambios de mercado, moneda o semántica requieren una identidad nueva. Una corrección excepcional requiere una migración explícita, con backup y auditoría.

Los `CHECK` de IDs rechazan vacío y espacios exteriores sin cambiar el contenido. No se aplica `lower()`, `upper()` ni otra normalización a IDs, mercados, símbolos o direcciones. La comprobación de mayúsculas solo se aplica a `quote_currency`, conforme al modelo V0.4.1.

`ingestion_batches_must_start` rechaza la inserción directa de lotes terminales. Un lote solo puede nacer como `started`; luego puede pasar una vez a `succeeded`, `failed` o `abandoned`. `ingestion_batches_validate_finalization` protege `batch_id`, `series_id` y `started_at_utc`; los tres son inmutables. `source_reference`, `raw_payload_sha256` y `received_at_utc` pueden estar presentes al crear el lote o pasar de `NULL` a un valor al finalizar, pero un valor existente nunca puede cambiarse ni borrarse.

Al finalizar como `succeeded`, el trigger exige que `rows_inserted + rows_revised` coincida con el número real de filas de `bar_versions` asociadas al lote y que todos los contadores sumen `rows_received`. Esto admite lotes vacíos (0/0/0/0) e idempotentes (`rows_unchanged = rows_received`). Al finalizar como `failed` o `abandoned`, no puede existir ninguna vela del lote y los contadores de filas confirmadas son cero. El lote fallido se registra solo después del rollback de la transacción de datos.

Para evitar una actualización intermedia del lote `started`, `received_at_utc`, `source_reference` y `raw_payload_sha256` se establecen al crear el lote si ya se conocen; de lo contrario, se conservan en memoria y se escriben en la transición final. La hora de ingesta de las velas no puede ser anterior a `received_at_utc`. Un fallo de red sin respuesta deja recepción/hash en `NULL`; un error posterior a recibir datos puede guardar su recepción/hash al pasar a `failed`.

La relación diferida compuesta `(ingestion_batch_id, batch_commit_state)` → `(ingestion_batches.batch_id, ingestion_batches.status)` añade una garantía de atomicidad: cada vela declara `batch_commit_state = 'succeeded'`, pero el trigger de inserción solo permite crearla mientras el lote está `started`. La FK `DEFERRABLE INITIALLY DEFERRED` exige que, antes del `COMMIT`, el mismo lote haya pasado a `succeeded`. Si se intenta confirmar velas dejando el lote `started`, o pasándolo a `failed`/`abandoned`, el commit falla y debe hacerse rollback. El filtro as-of por `batch.status = 'succeeded'` sigue siendo una defensa adicional.

`bar_version_id` es `INTEGER PRIMARY KEY AUTOINCREMENT` y lo asigna SQLite; la aplicación nunca lo proporciona manualmente. Bajo el único escritor y `BEGIN IMMEDIATE`, funciona como secuencia lógica creciente de versiones confirmadas. Puede haber huecos por rollbacks; no se reutiliza el orden de un `batch_id` textual para ordenar versiones. La restricción única `(ingestion_batch_id, series_id, bar_start_utc)` impide insertar dos revisiones de la misma vela dentro de un mismo lote.

## 3. Serialización exacta de `Decimal`

### Reglas canónicas

La serialización se construye directamente desde `Decimal.as_tuple()`. No usa `normalize()`, `quantize()`, aritmética Decimal, `format()` ni operaciones sujetas a la precisión del contexto.

1. Rechazar primero valores no finitos (`NaN`, `Infinity`, `-Infinity`).
2. Leer `sign`, `digits` y `exponent` de `as_tuple()`.
3. Si todos los dígitos son cero, devolver exactamente `0`, ignorando el signo y exponente. Así `0`, `-0`, `0E-30` y `-0.000` comparten una representación.
4. Eliminar ceros iniciales del coeficiente si existen.
5. Eliminar ceros finales no significativos del coeficiente. Por cada cero eliminado, incrementar el exponente decimal en uno.
6. Sea `D` la secuencia restante de dígitos y `E = exponent + len(D) - 1` el exponente ajustado.
7. El significando es el primer dígito de `D`, seguido por `.` y los dígitos restantes si los hay.
8. Anteponer `-` si el signo de `Decimal.as_tuple()` es uno. Los positivos no llevan signo `+` ante el significando.
9. Añadir `e`, seguido siempre del exponente con signo explícito: `+` o `-`, sin ceros iniciales en su magnitud.

La forma final es:

```text
[-]d[.dígitos-significativos]e[+|-]exponente
```

Ejemplos:

| Entrada Decimal | Forma canónica |
|---|---|
| `1.2300` | `1.23e+0` |
| `0.00120` | `1.2e-3` |
| `1000` | `1e+3` |
| `-12.5` | `-1.25e+1` |
| `0`, `-0`, `-0E-50` | `0` |

El exponente se escribe como entero decimal de Python derivado de los componentes de la tupla; el signo positivo se escribe explícitamente y no se usan ceros de relleno. No se expande el número en una cadena de ceros, por lo que exponentes muy pequeños o grandes no causan pérdida de precisión ni expansión innecesaria.

### Recuperación sin pérdida

El texto canónico se guarda en columnas `TEXT` y se reconstruye con `Decimal(text)`. El analizador Decimal lee todos los dígitos y el exponente de forma exacta, sin redondeo por contexto. Valores con más de 30 dígitos significativos se conservan completos porque el algoritmo concatena los dígitos de la tupla y no los convierte a `float` ni realiza operaciones Decimal.

Los precios deben ser positivos y finitos; el volumen, si existe, debe ser no negativo y finito. Esas validaciones se ejecutan en Python mediante el modelo antes de insertar. El tipo textual de SQLite por sí solo no demuestra que un texto sea un Decimal válido.

## 4. Hashes deterministas

Cada vela recibe un SHA-256 del payload normalizado. La serialización del payload:

- incluye una etiqueta de formato, por ejemplo `bar-payload-v1`;
- usa JSON con claves ordenadas, separadores fijos `(",", ":")`, codificación UTF-8 y `ensure_ascii=False`;
- serializa Decimal con las reglas canónicas anteriores, como cadenas;
- serializa enum por su valor estable;
- serializa fechas y horas UTC como `YYYY-MM-DDTHH:MM:SS.ffffffZ`, y fechas de sesión como `YYYY-MM-DD`;
- incluye serie, intervalo/ajuste/unidad, límites temporales, OHLCV, estado cerrado y publicación del proveedor cuando exista;
- excluye batch ID, hora de recepción e ingesta para que una repetición idéntica no se convierta en una revisión.

El hash del cuerpo original descargado, cuando existe, se calcula aparte sobre sus bytes sin modificar. El hash de payload normalizado detecta cambios de datos ya interpretados; el hash de respuesta permite identificar el lote recibido.

`hash_version`/la etiqueta del payload identifica el formato del hash. `PRAGMA user_version` identifica el esquema de base de datos. Son versiones diferentes. No se comparan silenciosamente hashes generados con formatos distintos.

## 5. Versiones históricas y consultas as-of

La clave lógica de una vela es `(series_id, bar_start_utc)`. El hash se compara con la última revisión de esa misma clave:

- mismo hash que la última versión: idempotente, no se crea otra versión;
- distinto hash: se inserta una nueva versión con `revision_no + 1` y `supersedes_version_id`;
- A → B → A: se almacenan tres versiones; una repetición posterior de A no crea una cuarta.

No se declara `UNIQUE` sobre el hash histórico: hacerlo impediría registrar A → B → A. La secuencia de revisiones queda protegida por las restricciones y el trigger.

`revision_no` y `supersedes_version_id` definen el orden lógico por vela. `bar_version_id` da el orden secuencial global y no depende del reloj ni del `batch_id`. El trigger `bar_versions_validate_ingest_time` exige que cada vela tenga una hora no anterior al inicio y, si ya se conoce, a la recepción del lote; exige además que cada lote nuevo de una serie sea estrictamente posterior a todas las ingestas de otros lotes de esa serie. Esto se aplica también a `revision_no = 1`.

Todas las velas de un lote comparten la misma `ingested_at_utc`. Se permite ese empate dentro del lote porque sus versiones y el cambio del lote a `succeeded` se confirman atómicamente. Entre lotes distintos de la misma serie el empate se rechaza. La misma vela no puede aparecer dos veces en un lote. Por tanto, las revisiones A → B → A pertenecen a lotes distintos, tienen marcas de ingesta estrictamente crecientes y mantienen `revision_no`/`supersedes_version_id`.

La capa de almacenamiento calcula una sola marca efectiva por lote, después de la validación y justo antes de las escrituras finales: el máximo entre `utc_now`, `started_at_utc`, `received_at_utc` si existe y la última ingesta de la serie más un microsegundo. Si el reloj retrocede, la marca avanza desde la última ingesta; los triggers rechazan cualquier cálculo que no respete el orden. La marca se toma antes de insertar y confirmar, así que **no equivale necesariamente al instante exacto en que el COMMIT se vuelve visible**. La consulta temporal es una aproximación; la reproducción exacta usa el watermark de `bar_version_id`.

Los `bar_version_id` se generan dentro de transacciones de escritura serializadas. El estado de una transacción completa —todas sus velas y el lote `succeeded`— se hace visible de una vez. Los IDs asignados por una transacción no confirmada no son visibles a lectores externos; un rollback puede dejar huecos o reutilizar un ID que nunca llegó a confirmarse, pero no cambia ningún watermark previamente capturado.

Los tiempos significan:

- `bar_start_utc`/`bar_end_utc`: tiempo de mercado de la vela;
- `provider_published_at_utc`: publicación declarada por el proveedor, nullable;
- `received_at_utc` del lote: recepción del contenido por el agente;
- `ingested_at_utc` de cada versión: persistencia lógica del dato en nuestro sistema, monótona respecto a su versión predecesora.

Todas las marcas UTC almacenadas como texto usan el formato fijo `YYYY-MM-DDTHH:MM:SS.ffffffZ`, con UTC explícito y seis dígitos de microsegundos. La capa de almacenamiento parsea y valida el instante antes de persistir; las comparaciones de texto e índices asumen exclusivamente este formato. `batch_id` es un identificador de procedencia, no un reloj ni una secuencia.

Los `CHECK`/`GLOB` exigen la forma textual y rechazan separadores alternativos, formatos abreviados y espacios. `GLOB` no demuestra que exista la fecha —por ejemplo, puede aceptar un día 99—. Antes de escribir, Python parsea cada UTC con `datetime.fromisoformat` tras adaptar la `Z` a `+00:00`, exige offset cero y comprueba que al volver a serializar con seis microsegundos y `Z` se obtiene exactamente la cadena original. `session_date` se valida con `date.fromisoformat` y se exige que `parsed.isoformat()` coincida exactamente con la entrada.

El filtro de reproducibilidad siempre aplica `ingested_at_utc <= :cutoff`. Si se conoce la publicación del proveedor, exige también `provider_published_at_utc <= :cutoff`. Si no se conoce, se deja `NULL`; no se infiere que una vela estaba disponible al cierre ni se retrotrae la fecha de una descarga histórica. `received_at_utc` es la hora observada de recepción y no reemplaza ni la publicación del proveedor ni la ingesta.

La API ofrecerá dos formas de recuperar datos:

- `load_series_as_of_time(series_id, cutoff_utc)`: reproducibilidad temporal aproximada, sujeta a la resolución del reloj y al intervalo entre asignar la marca y el `COMMIT`.
- `load_series_as_of_version(series_id, max_bar_version_id)`: reproducción exacta del estado de datos confirmado y visible en un snapshot de SQLite.

El watermark se captura dentro de una transacción de lectura consistente:

```sql
SELECT COALESCE(MAX(bar_version_id), 0) AS max_bar_version_id
FROM bar_versions;
```

Un máximo global de `bar_version_id` es suficiente para reconstruir las versiones de velas confirmadas a través de varias transacciones, porque los IDs son globales, se asignan solo a versiones inmutables y las transacciones exponen todas sus filas o ninguna. Las consultas as-of filtran también por lote `succeeded`, cuya transición se confirma en la misma transacción que sus velas. Los lotes vacíos/idempotentes no cambian el conjunto de datos y los rollbacks no exponen filas. No se necesita una tabla de snapshots ni ordenar por `batch_id`.

El API captura el watermark y consulta las series dentro del mismo snapshot de lectura, o conserva el watermark para repetir consultas posteriores. Si la decisión futura evalúa varias series, se registra y reutiliza un único máximo global para todas. La marca temporal por sí sola no reproduce con exactitud el instante de visibilidad del commit.

El watermark reproduce el conjunto de versiones de mercado, no la selección de instrumentos/universo, estrategia, configuración o evidencia externa de una decisión. El futuro registro de decisiones deberá conservar también los `series_id`/instrumentos consultados y la versión de configuración aplicable.

Para obtener la serie as-of se escoge, por cada `(series_id, bar_start_utc)`, la versión elegible más reciente hasta el límite temporal y/o watermark. Solo se devuelven versiones pertenecientes a lotes `succeeded`:

```sql
SELECT b.*
FROM bar_versions AS b
JOIN ingestion_batches AS batch
  ON batch.batch_id = b.ingestion_batch_id
WHERE b.series_id = :series_id
  AND batch.status = 'succeeded'
  AND (:cutoff_utc IS NULL OR b.ingested_at_utc <= :cutoff_utc)
  AND (
      :max_bar_version_id IS NULL
      OR b.bar_version_id <= :max_bar_version_id
  )
  AND (
      :cutoff_utc IS NULL
      OR b.provider_published_at_utc IS NULL
      OR b.provider_published_at_utc <= :cutoff_utc
  )
  AND NOT EXISTS (
      SELECT 1
      FROM bar_versions AS newer
      JOIN ingestion_batches AS newer_batch
        ON newer_batch.batch_id = newer.ingestion_batch_id
      WHERE newer.series_id = b.series_id
        AND newer.bar_start_utc = b.bar_start_utc
        AND newer_batch.status = 'succeeded'
        AND (
            :cutoff_utc IS NULL
            OR newer.ingested_at_utc <= :cutoff_utc
        )
        AND (
            :max_bar_version_id IS NULL
            OR newer.bar_version_id <= :max_bar_version_id
        )
        AND (
            :cutoff_utc IS NULL
            OR newer.provider_published_at_utc IS NULL
            OR newer.provider_published_at_utc <= :cutoff_utc
        )
        AND newer.bar_version_id > b.bar_version_id
  )
ORDER BY b.bar_start_utc;
```

La API exige que al menos uno de `cutoff_utc` y `max_bar_version_id` esté especificado; ambos pueden especificarse para intersectar las dos condiciones. Un límite de versión `0` devuelve una serie vacía. Una consulta usa un solo `series_id`; no combina proveedores. Para revisar discrepancias entre fuentes se comparan explícitamente series del mismo activo, moneda de cotización y semántica temporal/ajuste compatibles, sin promediar ni sustituir valores.

## 6. Transacciones, rollback y lotes fallidos

El intento se registra independientemente de la transacción que inserta velas:

1. Crear un lote `started` y confirmarlo en una transacción pequeña.
2. Obtener/recibir y validar los datos. Mantener en memoria `received_at_utc`, `source_reference` y el hash de respuesta si aún no están persistidos.
3. Abrir la transacción de escritura con `BEGIN IMMEDIATE`; volver a leer el estado vigente, construir la serie candidata y validarla.
4. Después de validar y justo antes de las escrituras finales, calcular una sola `effective_ingested_at` para todo el lote. Debe ser `max(utc_now, started_at_utc, received_at_utc si existe, latest_series_ingested_at + 1 microsegundo si existe)`. Insertar todas las velas del lote con esa misma hora.
5. En esa misma transacción, pasar el lote a `succeeded`, guardar los campos de recepción/procedencia que faltaban y los contadores; los triggers comprueban que las filas reales y los contadores coincidan. Confirmar inmediatamente.
6. Si ocurre un error, hacer rollback de todas las velas y, en una transacción nueva, pasar el lote persistente a `failed`, guardando el error y los datos de recepción disponibles. Las filas insertadas/revisadas confirmadas son cero.
7. Si el proceso termina abruptamente, el lote `started` queda como tal hasta recuperación; solo se marca `abandoned` si no conserva velas, nunca se interpreta como éxito.

Esto evita la contradicción entre rollback completo y registro persistente del error. Si la propia base no se puede abrir o escribir, no se puede garantizar el registro en ella; el error debe propagarse y registrarse en el log externo de la aplicación.

Activar `PRAGMA foreign_keys = ON` en cada conexión. `BEGIN IMMEDIATE` serializa los escritores durante la validación final y la inserción. Las consultas y escrituras deben usar parámetros SQL. Los errores guardados no deben incluir credenciales ni secretos.

### Validación de la serie

Se reutiliza `validate_bar_sequence` de V0.4.1:

1. Rechazar cualquier vela cuyo `status` no sea `CLOSED`.
2. Confirmar que proveedor/fuente de cada vela coincidan exactamente con la fuente registrada.
3. Rechazar claves de inicio duplicadas o contradictorias dentro del lote.
4. Cargar la última versión vigente de cada vela de esa misma serie.
5. Aplicar en memoria las observaciones entrantes y correcciones; ordenar por `start_utc`.
6. Construir el `Instrument` para esa fuente —el modelo actual incluye proveedor y símbolo— y validar la serie candidata completa con `validate_bar_sequence`.
7. Insertar solo si todas las validaciones pasan.

Así una corrección también se verifica contra las velas vecinas y no puede dejar solapamientos, sesiones desordenadas ni mezclar intervalos, ajuste, volumen, fuente o proveedor.

## 7. Integración futura con Kraken

El adaptador actual de [kraken.py](../../investment_agent/market_data/kraken.py) mantiene una API de cierres en `float` y escribe CSV `date,close`. Se conservarán sus funciones y comportamiento. Se añadirá una función nueva para OHLCV que:

Tras migrar o restaurar:

2. ejecutar `PRAGMA integrity_check` y exigir `ok`;

## 10. Pruebas y criterios de aceptación

Las pruebas usan bases temporales fuera del repositorio y no hacen llamadas de red.

- **Decimal:** round-trip exacto de tokens pequeños y valores con más de 30 dígitos; `-0` y ceros equivalentes; rechazar no finitos; hash idéntico para formas equivalentes canónicas.
- **Hash:** mismo payload normalizado produce los mismos bytes/hash; cambios de campo o versión de serialización producen el comportamiento esperado.
- **Identidades:** `UPDATE` y `DELETE` son rechazados en `assets`, `instruments`, `data_sources` y `series`; insertar IDs nuevos sí funciona. IDs vacíos o con espacios exteriores fallan, y direcciones Solana que solo difieren en mayúsculas permanecen distintas.
- **Lotes:** insertar directamente un lote terminal falla; `batch_id`, `series_id` y `started_at_utc` no pueden cambiar. Campos de recepción/procedencia solo se establecen al crear el lote o pasar de `NULL` a valor al finalizar. Un lote exitoso contabiliza todas sus filas y sus versiones reales; `failed`/`abandoned` no retienen velas. Lotes vacíos `0/0/0/0` e idempotentes (`rows_unchanged = rows_received`) pasan; tras rollback, `failed` queda registrado.
- **Fechas:** los `CHECK`/`GLOB` de SQLite rechazan UTC que no tenga exactamente `YYYY-MM-DDTHH:MM:SS.ffffffZ` y `session_date` que no tenga exactamente `YYYY-MM-DD`. La validación Python rechaza además fechas calendáricas inexistentes aunque tengan la forma correcta; probar ambas capas por separado.
- **Idempotencia:** repetir un lote sin cambios no añade versiones.
- **A → B → A:** conserva las tres revisiones y el enlace; repetir el último A no añade una cuarta.
- **Orden de ingesta:** también para `revision_no = 1`, rechazar horas anteriores a `started_at_utc` o a `received_at_utc` si existe. Para cualquier vela nueva de la serie, rechazar una hora igual o anterior a la de un lote previo; todas las velas del mismo lote deben compartir hora. Verificar que cambiar `started_at_utc` al finalizar el lote se rechaza, que una hora previa a `COMMIT` es solo aproximada y que `max_bar_version_id` reproduce el estado confirmado sin ordenar por `batch_id`. Probar reloj atrasado (la aplicación usa la última ingesta + 1 microsegundo), timestamp anterior al lote, empate entre lotes y empate dentro del mismo lote.
- **As-of temporal:** corte anterior a una ingesta no devuelve esa versión; el corte posterior la devuelve; la publicación futura se excluye; datos descargados hoy no aparecen en cortes anteriores a la ingesta. Validar también que solo se devuelvan lotes `succeeded`.
- **Watermark:** capturar un `max_bar_version_id` en un snapshot de lectura, ejecutar varias transacciones de escritura posteriores y comprobar que `load_series_as_of_version` con ese límite devuelve exactamente el conjunto previo. Comprobar transacciones atómicas de varias velas, rollbacks y lectura de varias series con el mismo watermark.
- **Formato temporal:** rechazar `'2025-1-9 10:00'`, `'2025-01-05 00:00'`, espacios y fechas imposibles después de validación Python; los GLOB SQL bloquean las formas estructuralmente incorrectas.
- **Velas incompletas:** rechazo antes de persistir; lote fallido visible y ninguna vela insertada.
- **Proveedores:** fuentes separadas para el mismo activo; dos cierres distintos en el mismo instante permanecen separados; no se crea una serie combinada.
- **Cotizaciones:** BTC/USD y BTC/EUR son instrumentos diferentes y no pueden compartir serie.
- **Validación secuencial:** inserciones y correcciones comprueban la serie final completa; solapamientos, incompatibilidades y errores de proveedor/fuente se rechazan.
- **Transacción:** inyectar una falla después de insertar una fila candidata produce rollback total de velas y persiste el lote fallido por separado.
- **Backup/integridad:** copia y restauración reproducen datos y revisiones; `integrity_check` devuelve `ok`; claves foráneas activas.
- **Git:** confirmar que base, WAL/SHM, diarios y respaldos quedan ignorados antes de generar datos.
- **Kraken:** valores decimales extraídos del cuerpo original sin `float`; OHLCV exacto, cierre de vela y descarte de la abierta; pruebas existentes del CSV no cambian.
- **Compatibilidad:** todas las 66 pruebas V0.4.1 siguen pasando y las 12 cifras históricas de referencia de V0.3 permanecen idénticas. Los valores esperados deben fijarse con la referencia confiable anterior a la implementación, no regenerarse desde el código nuevo.

## 11. Riesgos pendientes

- Kraken no publica en el endpoint usado el momento histórico de disponibilidad de cada corrección; si no hay publicación verificable, solo se puede afirmar cuándo la recibió nuestro sistema.
- Retención y paginación del endpoint deben verificarse antes de diseñar una descarga completa.
- La identidad canónica de activos, listados y calendarios necesita un registro explícito; no debe inferirse solo del ticker.
- SQLite es para almacenamiento local de un escritor a la vez; una evolución multiusuario o con muchos escritores puede requerir otro motor.
- `integrity_check` no sustituye copias independientes ni pruebas periódicas de restauración.
- Hashes y texto Decimal conservan el dato recibido, pero no prueban que el proveedor tuviera razón; la procedencia y la comparación entre fuentes siguen siendo necesarias.
